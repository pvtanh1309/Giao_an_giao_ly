# Dark Mode Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add an accessible, persistent dark theme without changing layout, lesson formatting, or backend behavior.

**Architecture:** Pure preference helpers own `system | light | dark`, storage, and pre-hydration logic. A client ThemeProvider applies `.dark`, follows system/storage events, and exposes a header toggle. Existing CSS tokens provide the palette; scoped overrides handle fixed light surfaces while lesson canvases remain warm paper.

**Tech Stack:** Next.js App Router, React context/hooks, TypeScript, CSS custom properties, Node.js built-in test runner.

**Spec:** `docs/superpowers/specs/2026-10-18-dark-mode-design.md`

## Global Constraints

- Follow the device preference until an explicit choice is saved; persist explicit choices in `localStorage` and synchronize same-browser tabs.
- Apply theme before first paint; preserve layout, church identity, authored formatting, and print/export output.
- Theme navigation, dashboard, lists, tables, forms, menus, dialogs, profile screens, and editor controls.
- Keep lesson canvases warm paper and authored content unchanged; respect reduced motion for transitions.
- Frontend presentation only; no backend, API, or account-level preference changes.

## Review Focus

- Invalid/unavailable storage: fall back to the device preference without throwing (Task 1 tests).
- Saved theme at first paint: apply class before hydration without mismatch (Task 2 tests and Task 6 browser check).
- Cross-tab and system changes: sync only while no explicit choice overrides system (Task 6 browser check).
- Portaled dialogs: inherit root theme class (Task 6 browser check).
- Authored colors and print: preserve paper canvas, inline styles, cell colors, and print output (Task 5 tests and Task 6 check).
